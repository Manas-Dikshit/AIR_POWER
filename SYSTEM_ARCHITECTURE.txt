1. PROBLEM CONTEXT AND SOLUTION SUMMARY
--------------------------------------------------------------------------------

Air-force support operations have to answer one question every day:

    "Given aircraft readiness, crew availability, support inventories,
     weather/airspace restrictions and task priorities — who flies what,
     and why?"

Answering it by hand is slow, inconsistent and hard to justify. The failure
modes are concrete: double-booked airframes, tasks left unassigned with no
stated reason, stale plans applied against data that has since changed, and a
decision trail nobody can reconstruct.

AIR POWER is a decision-support dashboard that:

  * tracks fleet readiness, crew status, support resources, simulated regions
    and operational tasks with priorities and time windows;
  * converts the whole picture into a deterministic, explainable allocation
    plan — every recommendation carries a score (0-100) built from four
    published terms and a plain-English explanation;
  * simulates what-if events (aircraft unavailable, weather, airspace,
    maintenance delay) and produces revised plans;
  * refuses to apply a plan generated against stale data;
  * keeps an audit trail of every change (activity log).

The system is a recommendation engine, not an autopilot: the operator always
reviews and explicitly applies a plan. Nothing here connects to a real system;
every aircraft, crew member, task, region and quantity is synthetic demo data.

Core design decisions:

  1. The allocation engine (src/lib/allocation.ts) is a PURE function — no
     database, no clock of its own (the current time is injected), no
     randomness. Same inputs => same plan, always.
  2. Exactly one orchestrator (src/services/operations-orchestrator.ts) owns
     every read and write path. The UI and the API never talk to the database
     directly for business operations.
  3. Every recommendation is explainable: score breakdown + human-readable
     reason. Rejections are never silent — blocked and unassigned tasks each
     carry the constraint that stopped them.
  4. Safety over convenience: stale-plan rejection, prebooking of committed
     assignments, transactional apply, and an explicit release ledger for
     resources when tasks leave the assigned state.


--------------------------------------------------------------------------------
2. DESIGN PRINCIPLES
--------------------------------------------------------------------------------

  Determinism        Pure engine + injected clock => identical inputs yield
                     identical plans. This is what makes results testable and
                     trustworthy in a review meeting.

  Explainability     Four transparent score terms (priority, readiness,
                     time-window fit, efficiency) and a generated sentence per
                     assignment and per rejection.

  Single writer      Only the orchestrator + plan store mutate operational
                     state. Route handlers are thin adapters.

  Guardrails first   Stale plans are refused, committed bookings are reserved,
                     policy thresholds live in one file (src/lib/policy.ts),
                     and applying a plan is a single database transaction.

  Simulation-safe    The entire dataset is synthetic; the UI carries a standing
                     "simulation environment" notice. No real-world feeds.

  Test localisation  Engine rules are unit-tested without a database; service
                     flows are integration-tested against the same SQLite file
                     the demo uses.

      SimulatedRegion and OperationalTask (sha1, first 12 chars). Any write to

6. ALLOCATION ENGINE — INTERNALS (src/lib/allocation.ts)
--------------------------------------------------------------------------------

  Input:  now (injected), aircraft, crew, resources, regions, tasks,
          minReadiness (default from policy), prebooked (committed bookings
          from the plan in force).

  Nature: greedy, priority-ordered. Tasks are processed CRITICAL -> HIGH ->
          MEDIUM -> LOW, ties broken by earliest window, then by task id
          (deterministic). Each task is served by the best-scoring triple that
          satisfies every hard constraint, then those resources are booked so
          later tasks cannot double-book them.

  The algorithm is deliberately NOT claimed to be globally optimal. A greedy
  pass can let a lower-priority task lose resources it could have used well.
  That trade-off is visible: losing tasks are reported with the reason.

  PER-TASK PIPELINE (first failure wins; each has a precise message):

    Step 0  Task status PENDING / RECOMMENDED / BLOCKED?      -> else SKIPPED
            (ASSIGNED tasks are committed elsewhere; COMPLETED/CANCELLED
             are closed.)
    Step 1  Region exists?                                    -> else BLOCKED
    Step 2  Region policy: weather/airspace restriction blocks this task
            category (src/lib/policy.ts)?                     -> else BLOCKED
    Step 3  Any aircraft of the required category at all?     -> else BLOCKED
    Step 4  Usable aircraft now?
              status AVAILABLE or ASSIGNED (ASSIGNED = committed, reusable)
              readiness >= 60%
              readyAt(now) <= task.startsAt, where
              readyAt = max(now + turnaroundMinutes,
                            maintenanceCompletionAt)
                                                            -> else BLOCKED
              (reason text distinguishes: all under maintenance / turnaround
               cannot meet the window / below readiness minimum)
    Step 5  Crew with the required qualification on strength? -> else BLOCKED
            Crew usable now: status AVAILABLE and
            availableFrom <= task.startsAt                   -> else BLOCKED
    Step 6  Support resource category stocked?                -> else BLOCKED
            Resource usable: not UNAVAILABLE, remaining >= required qty,
            and (policy) availableQuantity >= minimumRequired -> else BLOCKED
    Step 7  Best candidates free in the task window (no booking overlap)?
                                                            -> else UNASSIGNED
    Step 8  Score every surviving (aircraft, crew, resource) combination;
            keep the best (ties: lowest ids — deterministic).

  SCORING (weights sum to 1; result scaled to 0..100, one decimal):

    score = 0.40 * priority          PRIORITY_WEIGHT: CRITICAL 1.0,
                                   + 0.20 * readiness            HIGH 0.75,
                                   + 0.20 * timeWindow           MEDIUM 0.5,
                                   + 0.20 * efficiency           LOW 0.25
      readiness  = readinessPercentage / 100
      timeWindow = clamp01(1 - turnaroundMinutes / 240)
                   (>= 240 min turnaround scores 0 on this term)
      efficiency = clamp01( (resourceFit + airframeSpread) / 2 )
                   resourceFit     = clamp01(required qty / remaining stock)
                                     (tight fit scores higher)
                   airframeSpread  = 1 / (1 + times this airframe is already
                                     booked in this run)
                                     (spreads work across the fleet)

  TASK OUTCOMES
    assignments : RECOMMENDED rows with score + breakdown + explanation
    blocked     : hard constraint failed (maintenance, qualification, policy,
                  category gap, support shortage) — cannot be planned at all
    unassigned  : constraints were satisfiable in principle, but compatible
                  aircraft/crew were already committed by higher-priority
                  tasks in this run
    skipped     : ASSIGNED (carried, see below) or closed tasks
    utilisation : aircraft/crew percentages + per-resource
                  consumed/remaining after the run
    violations  : standing data-quality/invariant findings, independent of
                  this plan's outcome:
                    READINESS_BELOW_MINIMUM, RESOURCE_BELOW_MINIMUM,
                    WEATHER_RESTRICTION, AIRSPACE_RESTRICTION,
                    FLEET_GAP, QUALIFICATION_GAP

  PREBOOKING AND CARRY-OVER
    * Prebooking: before a fresh run, the orchestrator loads the APPLIED
      plan's ASSIGNED rows (getPrebookedAssignments) and reserves those
      aircraft/crew time intervals and resource quantities up front. A replan
      therefore cannot silently steal a commitment that is still in force.
    * Carry-over: tasks that were already ASSIGNED are skipped by the engine
      but mirrored into the new plan as ASSIGNED rows ("carried over"), so the
      applied plan always lists every committed task. Summary counts them as
      "carried".

7. PLAN STORE (src/lib/plans.ts)
--------------------------------------------------------------------------------

  Persist:
    createPlan(dataVersion, outcome)
      One transaction: insert AllocationPlan(status=GENERATED, dataVersion,
      summary JSON) + all Allocation rows (carried ASSIGNED, fresh
      RECOMMENDED, and every BLOCKED/UNASSIGNED rejection with its reason).

  Validate before apply:
    validatePlanAssignments(allocations, liveData)
      Re-checks every row against live data at apply time:
        - task still exists; carried rows must still be ASSIGNED
        - RECOMMENDED tasks must still be plannable
        - aircraft: exists, status, category match, readiness >= 60%,
          maintenance done before window, no double-booking
        - crew: exists, status, qualification match, no double-booking
        - resource: exists, not UNAVAILABLE, >= minimum (policy),
          cumulative consumption <= availableQuantity
      Returns human-readable problems; non-empty => plan refused.

  Apply:
    applyPlan(planId) — guard sequence:
      404 plan not found
      409 plan already APPLIED
      409 plan SUPERSEDED
      409 dataVersion mismatch (stale) — details include both versions
      409 validation problems (list)
    Then one transaction:
      - all other APPLIED plans -> SUPERSEDED
      - each RECOMMENDED row  -> ASSIGNED; task -> ASSIGNED (notes cleared);
        aircraft/crew -> ASSIGNED; resource quantity decremented
        (LOW status if it drops under minimum)
      - BLOCKED/UNASSIGNED rows on plannable tasks: task -> BLOCKED or
        PENDING with the engine's explanation stored as constraintNotes
      - plan -> APPLIED + appliedAt
      - ActivityLog PLAN_APPLIED with counts

  Query:
    listPlans (last 25, with allocations + joined entities),
    getPlanById, getLatestAppliedPlan, getActiveAssignments,
    assignmentFingerprint (task -> "aircraft/crew" map for UI diffing).


--------------------------------------------------------------------------------
8. ORCHESTRATOR — WRITE-PATH BEHAVIOUR (src/services/operations-orchestrator.ts)
--------------------------------------------------------------------------------

  Every write follows the same shape:
      load current state -> validate -> mutate + side effects in ONE prisma
      transaction -> append ActivityLog -> return result + fresh dataVersion.

  updateAircraft(id, patch)
    Rules: cannot set AVAILABLE below 60% readiness;
           MAINTENANCE requires a future maintenance completion estimate;
           a non-MAINTENANCE airframe cannot keep a future estimate;
           UNAVAILABLE caps reported readiness at 25%.
    Side effect: flagTasksForAircraft — if the airframe became unusable, its
    tasks in the APPLIED plan are released and returned to PENDING with a
    review note ("Flagged for review: assigned aircraft AC-X is now ...").

  updateCrew(id, patch)
    Rules: availability status and "available from" must be consistent
    (a future available-from date is refused in either state).
    Side effect: flagTasksForCrew — same release-to-PENDING flow.

  updateResource(id, patch)
    Sets availableQuantity / minimumRequired; status recalculated to
    AVAILABLE or LOW by comparison. (No release logic; resources are only
    consumed/released through plan apply / releaseTaskAssignment.)

  createTask(input)
    Validates the region exists; assigns the next TASK-NNN id; status PENDING.
    Full field set comes from Zod (title, category, priority, required
    aircraft category, crew qualification, resource category + quantity,
    region, window, optional notes).

  updateTask(id, input)
    Window end must be after start; region must exist; a COMPLETED task can
    only be reopened as PENDING or CANCELLED; leaving ASSIGNED triggers
    releaseTaskAssignment. Logs TASK_STATUS_CHANGED or TASK_UPDATED.

  deleteTask(id)
    Releases if ASSIGNED, then deletes (allocations cascade).

  generateAllocationPlan()
    Refuses when there are no open tasks (422). Reads the dataset, stamps the
    current dataVersion, loads prebookings, runs the engine, persists the plan,
    logs PLAN_GENERATED.

  applyAllocationPlan(id)
    Delegates to the plan store's applyPlan (section 7).

  activateScenario(type, input)
    See section 9. Each scenario returns: initial conditions, the changes
    made, affected tasks with their notes, and the new dataVersion.

  resetDemoData()
    Re-runs the deterministic seed (fresh initial plan produced by the real
    engine) and logs DEMO_RESET.

9. SCENARIO SIMULATOR
--------------------------------------------------------------------------------

  Four what-if events; each mutates the simulated world inside one transaction
  and logs SCENARIO_ACTIVATED. Target selection: caller may pass aircraftId /
  regionId / hours; otherwise a sensible default is chosen.

  A. aircraft-unavailable
     Pick aircraft (or default: first ASSIGNED, else first AVAILABLE — refuses
     if already UNAVAILABLE). Sets UNAVAILABLE + readiness capped at 25% and
     releases every non-closed task it was committed to in the plan in force:
     task -> PENDING with "Reassigned for review" note.

  B. weather-restriction
     Pick region (default: busiest region still NORMAL). Sets weatherStatus =
     RESTRICTED. Open tasks of blocked categories (TRAINING, TRANSPORT) there
     are released and set BLOCKED with the policy reason.

  C. airspace-restriction
     Same mechanics for airspaceStatus = RESTRICTED; blocked categories are
     LOGISTICS and TRANSPORT (emergency supply is exempt).

  D. maintenance-delay
     Pick an aircraft under maintenance (default: first one). New estimate =
     max(old estimate, now) + hours (default 12, 1..72 via validation).
     Readiness drops by 15 points (floor 10). Tasks of that category starting
     before the new estimate are released to PENDING with a flag-for-review
     note.

  Weather/airspace rules are shared verbatim between the simulator and the
  engine via src/lib/policy.ts (isWeatherBlocked / isAirspaceBlocked /
  regionBlockReason), so the wording and the rule can never diverge.

  After any scenario the operator generates a REVISED PLAN: same pipeline,
  with the committed remainder prebooked, producing a diff against the applied
  plan (carried vs changed assignments).

10. CONSISTENCY, GUARDRAILS AND INVARIANTS
--------------------------------------------------------------------------------

  (1) Stale-plan rejection
      Plan carries dataVersion at generation time; apply compares against the
      live fingerprint. Mismatch => 409 "This plan is stale... Generate a
      fresh plan" (both versions in error details).

  (2) Double-apply / supersede protection
      A plan can be applied once; applying a new plan supersedes the previous
      APPLIED plan in the same transaction.

  (3) Prebooking
      Committed bookings are reserved before every fresh run (section 6), so
      replanning cannot silently steal an airframe or crew that is still
      flying.

  (4) Resource ledger
      Support quantities are decremented on apply and returned by
      releaseTaskAssignment whenever a task leaves ASSIGNED (manual edit,
      delete, scenario, or a fleet/crew change that invalidates it).
      Aircraft/crew flip back to AVAILABLE only if no other ASSIGNED row in
      the applied plan still needs them. Re-checked by validatePlanAssignments
      before apply.

  (5) Policy gates
      Readiness minimum 60%, weather/airspace category suspensions, resource
      deferral below configured minimum — all in src/lib/policy.ts. The fleet
      editor additionally refuses to mark a <60% airframe AVAILABLE.

  (6) Transactionality
      Every multi-row mutation runs in prisma.$transaction: plan apply,
      plan create, scenario activation, task edits, aircraft/crew/resource
      edits. Partial state is not observable.

  (7) Audit trail
      Append-only ActivityLog for every business event (see WORKFLOW.txt
      section 10 for the event catalogue).

12. UI ARCHITECTURE AND DESIGN LANGUAGE
--------------------------------------------------------------------------------

  * All six pages are client components that read through useApi(path) and
    mutate through apiPost/apiPatch/apiDelete. After any successful mutation
    the page calls notifyChanged(), which broadcasts an
    "airpower:changed" window event; every mounted useApi() refetches — cheap
    cross-module consistency without a client cache layer.
  * Feedback is first-class: toasts (ToastProvider), confirm dialogs for
    destructive actions (apply plan, reset), explicit loading / error / empty
    states, and status pills driven by the same vocabulary as the domain.
  * Design language: "hand-drawn on paper" — irregular sketch borders, ink
    palette (ink / paper / navy / accent), Caveat handwriting accents, dashed
    simulation-environment notice. Deliberately styled to read as a
    decision-support artifact, not a control console.
  * The shell shows the last generated plan's timestamp and status on every
    page, so plan state is never hidden from the operator.

13. SEED DATA DESIGN (src/lib/seed.ts)
--------------------------------------------------------------------------------

  The seed is fully deterministic (fixed ids, fixed hour offsets from "now")
  and covers every required demonstration case:

    12 aircraft  — 5 TRANSPORT (1 maintenance, 1 unavailable),
                   3 ROTARY (all under maintenance — temporary rotary gap),
                   2 SURVEILLANCE (1 unavailable),
                   2 TRAINER
    18 crew      — pilots per category, loadmasters, maintenance techs, with
                   deliberate unavailability
    8 support resources — including two deliberately below their configured
                   minimum (fuel bowser reserve RES-02, medical pallets
                   RES-06) to exercise the deferral rule
    4 regions    — Northern Corridor (airspace RESTRICTED),
                   Coastal Sector (weather RESTRICTED),
                   Central Highlands and Eastern Valley (clear)
    13 tasks     — the feasible critical medical resupply, logistics under the
                   restricted northern corridor, training under restricted
                   coastal weather, a rotary lift with no rotary airframe
                   currently serviceable, a task with no qualified crew, a
                   task deferred by resource minimums, and priority contention
                   for transport crews; plus one COMPLETED task for history

  After writing the rows, the seed RUNS THE REAL ENGINE and applies the
  resulting plan (backdated 2 hours), so the seeded world is always internally
  consistent with the allocator. It also writes seven narrative audit entries
  (scenario loaded, maintenance opened, advisories, resource low, task
  completed) so the activity log tells a story from the first launch.

  rules are provable without a database and service rules are provable end to
  end.


--------------------------------------------------------------------------------
15. SECURITY, SAFETY AND ENVIRONMENT
--------------------------------------------------------------------------------

  * Simulation-only by design: synthetic data, standing UI notice, no
    external feeds, no real-world identifiers.
  * Stateless front end: no user data persisted in the browser beyond the
    session's own view state.
  * Input trust boundary: every request body is Zod-validated (types, ranges,
    enums, date parsing, window ordering) before it reaches the service layer.
  * SQL safety via Prisma parameterised queries; no string-built SQL.
  * Error hygiene: unexpected errors are logged server-side and returned to
    the client as a generic 500 without internals.
  * Known limitation: no authentication / authorisation and no multi-user
    locking (single-operator demo; last write wins between concurrent editors,
    stale plans are caught by the data-version check).

16. DEPLOYMENT AND RUNTIME
--------------------------------------------------------------------------------

  Local/demo:
      npm install
      npm run setup          # prisma generate + db push + deterministic seed
      npm run dev            # http://localhost:3000

  Other scripts:
      npm run build / npm start      production build / serve
      npm run lint                   ESLint (flat config)
      npm test                       Vitest suite
      npm run db:reset               reseed demo data from scratch

  Configuration: single env var DATABASE_URL (SQLite file, default
  prisma/dev.db). Next.js 16 with Turbopack; turbopack.root is pinned in
  next.config.ts so the workspace root is never inferred outside the repo.
  Node.js 20+.

  Production path (out of scope for the demo): hosted Node server or
  serverless Next.js, Prisma migrated to PostgreSQL, auth in front of
  /api/**, scheduled generation, and a separate read replica for reporting.

18. LIMITATIONS AND FUTURE SCOPE
--------------------------------------------------------------------------------

  Current limitations
    * Greedy engine: fast and explainable, not globally optimal (stated in
      the UI copy and the docs).
    * Single-operator demo: no auth, no role separation, no concurrent-edit
      locking beyond the stale-plan check.
    * SQLite: single-writer, laptop-grade; fine for the demo, not for load.
    * All quantities are synthetic; no live telemetry or real-world feeds.

  Candidate extensions (NOT implemented)
    * Live operations map: plot the current (simulated) sortie state on a map
      of India — and, as a separate opt-in module, integrate a public ADS-B
      feed for real traffic awareness.
    * Swap SQLite -> PostgreSQL and add authentication + roles (planner /
      reviewer / auditor).
    * Scheduled auto-generation with operator approval queue.
    * Plan export (PDF/CSV) and e-mail notifications for blocked critical
      tasks.
    * What-if cost model (fuel burn, crew hours) as an additional score term,
      with the weights kept in src/lib/policy.ts.
